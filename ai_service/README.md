# Smart Library AI Service

The AI integration and orchestration module of the **AI-Powered Smart Library Management Assistant** (HCLTech Future Ready AI Engineer Hackathon).

It is a FastAPI service on `http://localhost:8002/api/v1` (port 8002; the backend uses 8001). It turns natural-language questions into **validated tool calls** against the library backend, then returns **grounded, cited, schema-stable** answers to the frontend.

It runs fully standalone against a mock backend. Switching to the real backend is a **configuration change only**.

---

## How it works

```
Frontend ──► POST /chat/messages ──► Orchestrator ─────────────► LLM (Gemini / fake)
                                        │   ▲                        │ "call tool X(args)"
                                        │   └──── tool results ◄──── ┘
                                        ▼
                               Tool executor
                     allowlist → JSON-schema args → auth/role
                     → confirmation gate → handler → result validation → audit log
                                        │
              ┌─────────────────────────┼──────────────────────────┐
              ▼                         ▼                          ▼
    LibraryToolAdapter            RAG retriever               Recommender
    mock (fixtures) │ http        FAISS + MiniLM              profile + RAG
                    ▼             (index built via adapter)   + live availability
           Backend :8000/api/v1
```

### Core rule

The LLM decides *which* tool to ask for. It never touches HTTP, the database, files or tokens.

Every fact the user sees comes from a tool result: titles, availability, loans and transaction results.

### Guarantees enforced in code, not in the prompt

| Concern | How it is enforced |
|---|---|
| No invented resources | Resources and citations are built from tool results. Resource IDs the model gives that no tool returned are dropped, and titles always come from the catalog. |
| No invented availability | `available_copies` appears only when an availability-bearing tool returned it. |
| No fake transactions | `create_reservation` and `renew_loan` only **propose** an action. Execution happens only via `POST /chat/actions/confirm`. For `needs_confirmation`, `refused` (tool denial), `not_found` and outage outcomes, the assistant message is generated by code. |
| Identity and privacy | No tool accepts a `user_id`, URL or token. Account tools always act as the authenticated caller. A pre-LLM guardrail refuses requests about other people's accounts. |
| Authorization | Role checks run in the executor (e.g. analytics is librarian-only). In HTTP mode the backend enforces them again. |
| Strict input validation | JSON Schema with `additionalProperties: false`. ID fields only accept plain IDs (no `/`, URLs or paths). Limits are capped. |
| Prompt injection | Retrieved document text is wrapped in `<<UNTRUSTED_CONTENT>>` markers. The structural controls above hold even if the model is fully fooled (tested). |
| Restricted content | The vector index stores each chunk's access level and filters by the caller's role at query time. |
| Bounded execution | At most `MAX_TOOL_CALLS` per message. After that, the model may only call `final_answer`. |
| Auditability | Each tool call logs one JSON line with `trace_id`, user, tool, redacted args, status, error code and latency. Every response carries a `trace_id`. |

## Quick start

Requires **Python 3.11 or later**; the service was developed on 3.13. On Windows, use `.venv\Scripts\python`.

```bash
cd ai_service
python -m venv .venv
.venv/Scripts/python -m pip install torch --index-url https://download.pytorch.org/whl/cpu   # optional: small CPU-only torch
.venv/Scripts/python -m pip install -r requirements.txt
cp .env.example .env            # then set GEMINI_API_KEY (or LLM_PROVIDER=fake)

.venv/Scripts/python -m app    # listens on SERVICE_HOST:SERVICE_PORT from .env (default 127.0.0.1:8002)
```

### Sharing with teammates over Tailscale

The default `127.0.0.1` is reachable only from your own PC. To let the frontend and backend teammates call the service:

1. Find your Tailscale IP with `tailscale ip -4` (e.g. `100.114.163.7`), and set it in `.env`:

   ```env
   SERVICE_HOST=100.114.163.7
   SERVICE_PORT=8002
   ```

2. Allow the port through Windows Firewall, for tailnet devices only. Run this once in an **Administrator** PowerShell:

   ```powershell
   New-NetFirewallRule -DisplayName "Smart Library AI (8002, Tailscale)" -Direction Inbound -Protocol TCP -LocalPort 8002 -Action Allow -Profile Private -RemoteAddress 100.64.0.0/10
   ```

3. Start the service with `.venv/Scripts/python -m app`, then share `http://<your-tailscale-ip>:8002/api/v1`. Teammates can check it at `/api/v1/health` and `/docs`.

### No API key?

Set `LLM_PROVIDER=fake` to use a deterministic, offline, rule-based model. It is good for demos and for the frontend team.

Set `EMBEDDING_MODEL=hashing` to skip the embedding model download.

## API (for the frontend)

All responses use the shared envelope:

- **Success:** `{status: "success", data, trace_id}`
- **Error:** `{status: "error", error: {code, message}, trace_id}`

### `POST /api/v1/chat/messages`

Request:

```json
{ "conversation_id": null, "message": "Recommend beginner resources for learning generative AI that are currently available." }
```

Response `data`:

```json
{
  "conversation_id": "conv-…",
  "outcome": "answered",
  "assistant_message": "…",
  "intent": "recommendation",
  "resources": [
    { "resource_id": "res-021", "title": "Prompt Engineering for Generative AI",
      "reason": "Semantically relevant to …; matches your interest in generative ai; beginner level as requested. Catalog facts: beginner book by James Phoenix, Mike Taylor; 1 available at Central Library.",
      "available_copies": 1 }
  ],
  "citations": [ { "resource_id": "res-021", "source_type": "catalog", "source_id": "res-021", "title": "Prompt Engineering for Generative AI" } ],
  "proposed_action": null
}
```

#### Fields

**`outcome`** is one of:

| Value | Meaning | What the frontend should do |
|---|---|---|
| `answered` | Normal answer. | Show the message and resources. |
| `not_found` | Nothing matching exists in authorized sources. | Show the message. |
| `refused` | Privacy or authorization refusal. | Show the message. |
| `needs_confirmation` | An action has been proposed but not executed. | Show `proposed_action.description` with a Confirm button. |

**`intent`** is one of: `search`, `availability`, `recommendation`, `account`, `reservation`, `renewal`, `research`, `analytics`, `general` or `out_of_scope`.

**`available_copies`** is `null` unless it was verified live.

**`citations[].source_type`** is one of:
- `catalog`: a catalog record
- `document`: authorized full text
- a chunk citation, where `source_id` looks like `res-013#c1`

**`proposed_action`** looks like `{action_id, action_type: "reservation" | "renewal", resource_id, loan_id, description}`.

Reuse the returned `conversation_id` for follow-up questions. Conversations are bound to their owner.

### `POST /api/v1/chat/actions/confirm`

Request:

```json
{ "action_id": "act-…" }
```

Response `data`:

```json
{ "action_id": "act-…", "action_type": "reservation", "transaction_status": "completed",
  "transaction_id": "rsv-8001", "reservation_id": "rsv-8001", "loan_id": null,
  "message": "Reservation confirmed: 'Prompt Engineering for Generative AI' is being held for you to pick up.",
  "details": { … } }
```

The request requires the same user who received the proposal. Actions expire after `ACTION_TTL_SECONDS` (default 300).

**`transaction_status`** is one of:

| Value | Meaning | Action afterwards |
|---|---|---|
| `completed` | The backend applied it. `transaction_id` is the reservation or loan ID. | Confirming again returns the same result; nothing runs twice. |
| `rejected` | A library rule refused it (e.g. not renewable, duplicate hold). `details.error_code` gives the reason. | Discarded. |
| `failed` | Temporary outage; nothing changed. | Kept, so retrying is safe: it reuses the same idempotency key. |

**Errors:**
- `401`: no token
- `404 action_not_found`: unknown, expired or someone else's action

### Other endpoints

| Endpoint | Purpose |
|---|---|
| `GET /api/v1/health` | `status` (`ok`, or `degraded` when the backend or LLM is unavailable), plus adapter mode, backend reachability, LLM readiness, embedder and indexed chunk count. |
| `POST /api/v1/index/refresh?full=false` | Librarian-only. Pulls new or updated resources into the vector index. This also runs automatically every `RAG_REFRESH_SECONDS`. |

### Service-level errors

| Status | Code | Cause |
|---|---|---|
| `401` | `http_401` | Invalid token |
| `404` | `conversation_not_found` | Conversation does not exist or belongs to someone else |
| `503` | `llm_unavailable` / `llm_not_configured` | LLM failed or is not configured |

## Connecting the real backend

The backend contract is the backend team's `BACKEND_API_HANDOFF.md` (2026-10-30). The backend runs on the backend owner's Mac and is reached over **Tailscale**.

Change `.env` only:

```env
TOOL_ADAPTER=http
LIBRARY_API_BASE_URL=http://100.83.115.82:8001/api/v1
```

### Before switching

1. Tailscale is running on your machine, and the backend Mac shows as active in `tailscale status`.
2. The backend owner has started the server bound to the Tailscale IP (`--host 100.83.115.82 --port 8001`). If it is bound to `127.0.0.1`, connections time out.
3. Check reachability: open `http://100.83.115.82:8001/api/v1/health`, or call this service's `GET /api/v1/health` and look for `backend_reachable: true`.

The backend uses port **8001** on its Mac; this AI service uses port **8002** on your machine.

### What the HTTP adapter does

- Calls the REST API with httpx and unwraps `{status, data, trace_id}`.
- Forwards the caller's own JWT. The frontend logs in with `POST /auth/login` and sends that token to this service. There is no shared AI identity.
- Validates tokens via `GET /auth/me`, cached for 60 seconds.
- Sends an `Idempotency-Key` on `POST /reservations` and `POST /loans/{id}/renew`. The key is generated once per proposed action and reused on every retry.
- On `409 database_busy`, retries twice with a short backoff using the same key. If it is still busy, the action stays pending so the user can confirm again safely.
- Logs the backend `trace_id` on errors. 5xx messages are never shown to users.

Prompts, tools, orchestration and the public chat API do not change.

### How the backend contract is used

| Contract detail | How the AI service handles it |
|---|---|
| `GET /resources?query=` is a literal case-insensitive substring filter ordered by `updated_at`, not by relevance | The `search_catalog` tool sends the whole phrase plus up to 4 keywords as parallel calls (limit 100 each). It merges results by `resource_id` and ranks them locally: title matches first, and most keywords must match. Every result is still a backend record. |
| `limit` 1–100 with `offset` paging; `updated_since` is strictly newer-than; no tombstones | The index refresh pages 100 at a time and de-duplicates by `resource_id`. It overlaps the time window by 5 minutes, skips unchanged records, and advances the watermark only after all pages succeed. Deleted resources are dropped at query time by re-checking `GET /resources/{id}`. |
| Content is `{resource_id, content, source, updated_at}`; access levels are `public`, `authenticated` and `restricted` (librarian only) | The tool pairs the content with live catalog metadata for titles and citations. Stored passages are re-checked against the **live** `access_level` before they are shown. |
| No service identity or AI API key exists | The indexer reads metadata and **public** content anonymously. Other content is fetched live with the caller's token through `get_resource_content`. `INDEXER_TOKEN` is optional. |
| `/me/profile` returns `courses[]` and `interests[]` | These are merged with the verified caller identity for recommendations. |
| Reservation status is `active`, `waitlisted`, `cancelled` or `fulfilled`; `queue_position` is set only when waitlisted | Confirmation texts use the returned status and position. |
| Priority waitlist: faculty, then researcher, then student, first-come within a role; a new request is ranked before a free copy is handed out | The preview shows the live queue size and says the position is confirmed by the library. The confirmation shows the real `queue_position` and notes that it can change. The mock adapter implements the same queue. |
| Only students, faculty and researchers may reserve or renew; librarians get 403 | `create_reservation` and `renew_loan` are restricted to patron roles, so librarians are refused before any backend call. |
| Renewal adds 28 days for faculty and 14 for students and researchers, at most twice; a non-owner gets 403 | The preview shows the role's period and the new due date. Pre-checks use the backend's `renewable` flag. A 403 becomes a refusal. |
| Analytics has no waitlist data ("rank availability by `waitlist_count`") | `get_library_analytics` adds `longest_waitlists`, built by paging the catalog and reading live availability (at most 10 requests at a time). |
| `fine_amount` is a decimal string | Parsed as `Decimal` and sent back as a string. |
| Analytics: `total_resources`, `active_loans`, `overdue_loans`, `active_reservations`, `popular_resources[]` | Passed through. Popular titles are grounded as resources and citations. |
| Error codes: `forbidden`, `duplicate_reservation`, `renewal_not_allowed`, `idempotency_conflict`, `database_busy`, `validation_error`, `internal_error` | Mapped to `permission_denied`, `conflict`, `not_renewable`, `conflict`, retryable `backend_error`, `invalid_argument` and `backend_error`. |

The mock adapter implements the same rules, so mock and HTTP behave the same. This is pinned by [tests/fake_backend.py](tests/fake_backend.py) and [tests/test_http_adapter.py](tests/test_http_adapter.py), which run the shared contract tests against both adapters.

RUN_MODEL_TESTS=1 .venv/Scripts/python -m pytest -q    # also checks the real MiniLM model

Tests use a scripted fake LLM, the mock adapter, an in-process fake backend and the offline hashing embedder.

```bash
.venv/Scripts/python -m eval.run_eval                      # uses .env (e.g. Gemini)
LLM_PROVIDER=fake .venv/Scripts/python -m eval.run_eval    # offline
```

It reports these metrics over 19 labelled cases in [eval/cases.json](eval/cases.json), and writes `eval/report.json`:

- outcome accuracy
- search relevance (hit@5)
- citation accuracy
- tool correctness
- availability correctness
- privacy
- latency p50/p95

## Known limitations

- **In-memory state.** Conversations, pending actions and the vector index live in memory, so a restart rebuilds the index (a few seconds) and drops pending actions. `FaissStore.save/load` exists for persistence but is not wired in. For multiple instances, use Redis for conversations and actions.
- **Model wording in `answered` responses.** For `answered` responses, the assistant's prose is model-written. Prompt rules constrain it, and the structured `resources`, `citations` and `available_copies` are always verified, but free text is not fact-checked word by word. The frontend should render facts from the structured fields.
- **Privacy guardrail coverage.** The guardrail is pattern-based and catches common phrasings. It is defense in depth: other users' data stays unreachable through tools regardless.
- **Deletion detection.** Incremental index refresh detects new and updated resources. Deleted resources are filtered out at query time through catalog verification, not removed from the index until a full refresh (`?full=true`).
- **Evaluation numbers.** Offline evaluation scores use the rule-based fake LLM, which was developed alongside these cases. Run `eval.run_eval` with Gemini for representative accuracy and latency.
